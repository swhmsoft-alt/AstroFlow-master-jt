# Image Catalog Workflow

> Placeholder-driven image system for the 23 service pages.
> Marketing drops 3 files per image into `public/images/hubs/`; the build picks them up automatically. No Cline involvement after the catalog entry is in place.

---

## 1. Why this exists

Before: 23 pages reused 10 stock photos. Generic, not authoritative, easy to mistake for a competitor.

After: every page has a unique image with a curated prompt and alt text, all driven from a single JSON catalog. Marketing owns the asset pipeline; engineering only owns the catalog row.

---

## 2. Architecture (3 layers)

```
pages  --catalogId-->  ImageTextSplit  --lookup-->  image-catalog.json
                                                       |
                                                       v
                            public/images/hubs/{category}/{filename}.{webp,png,svg}
                                                       ^
                                                       |
                                            scripts/check-image-catalog.mjs
                                            (three-way audit)
```

---

## 3. File inventory

| File | Role | Edit frequency |
|---|---|---|
| `src/content/image-catalog.json` | Source of truth. All 23 image specs. | When a new page needs an image, or alt/prompt needs tuning. |
| `src/components/ui/ImageTextSplit.astro` | Renders the `<img>` using `catalogId` lookup. | Rarely. Only when onerror chain or placeholder policy changes. |
| `src/pages/image-catalog/index.astro` | Dev-only status page. Shows on-disk check per row. | Never. |
| `scripts/check-image-catalog.mjs` | Three-way audit: catalog vs filesystem vs page refs. | Never. |
| `scripts/migrate-image-text-split.mjs` | One-shot: `imageSrc=` -> `catalogId=`. Idempotent. | Re-runnable, but not needed after first run. |
| `public/images/hubs/{category}/` | Where the actual asset files live. | Marketing writes here. |
| `memory-bank/image-catalog-status.md` | Auto-generated audit report. | Regenerated by the check script. |

Plus 2 small config touches:
- `astro.config.mjs` - `sitemap({ filter: ... && !page.includes('/image-catalog') })`
- `public/robots.txt` - `Disallow: /image-catalog/`

## 4. Catalog schema (`image-catalog.json`)

```json
{
  "id": "titanium-cnc-machining-services.hub",
  "page": "/titanium-cnc-machining-services/",
  "pageName": "Titanium CNC Machining Services (Hub)",
  "category": "titanium-cnc-machining-services",
  "filename": "hub",
  "webp": "/images/hubs/.../hub.webp",
  "png":  "/images/hubs/.../hub.png",
  "svg":  "/images/hubs/.../hub.svg",
  "alt":   "Grade 5 Ti-6Al-4V ...",
  "prompt":"Photorealistic industrial B2B ...",
  "decisionDim": "D1",
  "status": "placeholder",
  "priority": "P0"
}
```

### ID convention

`<category>.<leaf>` where `category` matches a directory under `public/images/hubs/`. The leaf for the hub page of a category is `hub`. For a leaf page, use the page's last slug segment.

Examples:
- `titanium-cnc-machining-services.hub` -> `/titanium-cnc-machining-services/`
- `titanium-cnc-machining-services.3-5-axis-cnc-machining` -> `/titanium-cnc-machining-services/3-5-axis-cnc-machining/`
- `branded-custom-packaging-services.hub` -> `/branded-custom-packaging-services/`

## 5. Workflows

### A. Marketing - make a new image

1. Read the `prompt` field for the row in `image-catalog.json` (or `/image-catalog/` in dev).
2. Generate the image (any tool). Target 3:2 aspect ratio, >= 1200 x 800 px.
3. Export three files: `webp` (<= 200 KB), `png` (fallback), `svg` (very simple line-art fallback, can be minimal).
4. Drop them into `public/images/hubs/{category}/{filename}.{ext}` - keep the same basename as in the catalog.
5. Run `node scripts/check-image-catalog.mjs` to verify; the row should flip from `[..] placeholder` to `[OK] real`.

### B. Engineering - add a new service page that needs an image

1. Add a row to `image-catalog.json` with all 11 fields. Pick `id` per convention.
2. Create `public/images/hubs/{category}/` with a `.gitkeep` if it does not exist.
3. In the new `.astro` page, use `<ImageTextSplit catalogId="<id>" ... />`. Do not pass `imageSrc` or `imageAlt`.
4. Run the check script - should report 0 dangling refs and 0 legacy refs.

### C. Migration: re-run on existing pages

```bash
node scripts/migrate-image-text-split.mjs
```

Idempotent. Skips pages that already have `catalogId`. Safe to re-run after a partial migration.

### D. Verification (CI / pre-commit)

```bash
node scripts/check-image-catalog.mjs
```

Exit codes:
- `0` - clean.
- `1` - real bug: missing file on disk (when `status: "real"`) or dangling `catalogId` page ref. Block merge.
- `2` - structural drift: orphan catalog entry, legacy `imageSrc` still present. Informational, not blocking.

The script also writes the full report to `memory-bank/image-catalog-status.md`.

## 7. Component contract (ImageTextSplit)

```ts
interface Props {
  catalogId?: string;     // preferred - looks up paths + alt from image-catalog.json
  imageSrc?: string;      // optional override for ad-hoc / marketing-test pages
  imageAlt?: string;      // optional override
  // ... existing props (eyebrow, title, body, bullets, ctaLabel, ctaHref,
  // imagePosition, background, badge, iconPath) unchanged
}
```

Rules:
- New pages must use `catalogId`. Never ship with `imageSrc=`.
- If both `catalogId` and `imageSrc` are passed, `catalogId` wins.
- If neither is passed, the component throws at build time (deliberate - forces a fix).
- On error in the browser, the `<img>` walks the fallback chain `webp -> png -> svg` (stored in `data-fb`). Once exhausted, the image hides and the parent card keeps its background.

## 8. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Image 404 in dev | File at the wrong path or wrong extension | Check `webp` path in `image-catalog.json`; verify with the `/image-catalog/` page |
| Image shows on hub but not on leaf | The leaf page has its own `catalogId`, not the hub's | Each page references its own id per ID convention |
| Check script says "missing on disk" | Marketing has not dropped the file yet | Either add the file, or change `status` to `placeholder` if intentional |
| Check script says "dangling page ref" | A page uses a `catalogId` that is not in the JSON | Add the row, or fix the typo |
| Check script says "orphan catalog entry" | A row exists that no page references | Either delete the row, or add the page |
| `/image-catalog/` shows nothing in prod | Expected - page is dev-only | Run `astro dev` instead |

---

## 9. Hard rules

1. Never use `imageSrc=` on `<ImageTextSplit>` for new pages. Use `catalogId`.
2. Never rename a `filename` or `category` in the JSON without also moving the files in `public/images/hubs/`. The 3 files per image are a hard contract.
3. Never inline `<script type="application/ld+json">` in any `.astro` page - schema authority lives in `src/lib/schema.ts` (see `SEMANTIC_CLOSURE.md`).
4. The `dev` visibility of `/image-catalog/` is intentional. Do not make it public; that route is internal diagnostics.
