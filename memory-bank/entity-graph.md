# Entity Graph — AstroFlow GEO Cluster×Inbound

> **Created:** 2026-08-24
> **Status:** Phase 1 of GEO Cluster×Inbound strategy complete. Build pipeline + coverage audit in place; internal-linking remediation pending.

---

## 1. Goal

Move from "build pages, hope they rank" to **knowledge-graph-based SEO**:
every entity (material / process / service / industry / standard / product / case-study / application)
exists once as a canonical record and is reachable through a **dense internal-link mesh**
that both humans and LLM crawlers (Google SGE, Perplexity, Bing Copilot) can traverse.

Three concrete deliverables:

1. **Canonical entity registry** — single source of truth, machine-readable.
2. **Coverage audit** — quantifies orphan entities & under-linked clusters.
3. **Remediation loop** — Phase 2 will close the orphan gap (internal-link generation).

## 3. Entity Schema

```ts
interface Entity {
  id: string;             // canonical: "<category>:<source>:<slug>" e.g. "material:grade:grade-5"
  slug: string;           // URL-friendly id (no category prefix)
  category: 'material' | 'standard' | 'process' | 'service'
          | 'industry' | 'application' | 'product' | 'case-study';
  subcategory?: string;   // e.g. "Alpha-Beta Titanium Alloy (α+β)"
  canonical_name: string; // "Grade 5 – Ti-6Al-4V Titanium Alloy" (en)
  chinese_name?: string;  // "Ti-6Al-4V 5级钛合金" (zh, if available)
  aliases: string[];      // 3-10 normalized aliases: Ti-6Al-4V, UNS R56400, AMS 4928 ...
  search_terms: string[]; // lower-case + normalized for fuzzy matching (used by audit)
  page_url: string;       // "/materials/grade-5/" — what internal links should target
  source_file: string;    // "src/data/titanium-grades.ts"
  source_collection: string; // "titanium-grades.ts" | "content/materials" | ...
  relationships: {
    conformsTo?: string[];    // standards
    usedIn?: string[];        // industries / applications
    usesMaterial?: string[];  // materials
    usesProcess?: string[];   // processes
    usesEquipment?: string[]; // equipment
    providesService?: string[]; // services
    hasCaseStudy?: string[];  // case-studies
    // resolved references are slugs (or entity IDs) — not full URLs
  };
}
```

**Cross-references** are computed during build by tokenizing each entity's canonical name + aliases
and matching substrings against the global registry. Limit: 20 refs per relationship array to keep
JSON size bounded (867 entities × ~50 refs ≈ 43k nodes if unbounded).

## 4. Build Pipeline

```
┌────────────────────────────┐
│ 11 data sources            │
│  - 4 TS files (data/)      │   regex TS-stripper
│  - 7 JSON collections      │   → vm.runInContext
│      (content/)            │   → walk objects
└─────────────┬──────────────┘
              │
              ▼
┌────────────────────────────┐
│ 867 entities in memory     │  + cross-ref resolver
│ (id, alias, page_url, ...) │  + alias normalizer
└─────────────┬──────────────┘
              │
              ▼
   data/entities/entity-registry.json   (compact JSON, no pretty-print)
```

### 4.1 TS-Stripping Strategy

Astro project already supports TS via `astro build`. But this script must run via plain `node`
with **zero new dependencies**. Solution: regex-based TS stripper + `vm.runInContext`.

Order matters — pipeline is fragile to reordering:

1. Strip `// line comments` and `/* block comments */`.
2. Strip `import` / `export type` / `export interface` declarations (multi-line aware).
3. Strip `export ` prefix from `export const X: T = ...` / `export const X = ...`.
   **Preserve the `:` so step 4 can handle the type annotation.**
4. Strip `const X: T = ...` and `let X: T = ...` type annotations.
   T can contain: `Record<K, V>`, `'A' | 'B'`, arrays, primitives.
5. Strip optional `?:` from object-literal fields inside `= { ... }`.
6. Strip `as Type` assertions.
7. Append `module.exports.X = X; module.exports.Y = Y; ...` for each collected identifier.
8. Inject global `module.exports = {}; const __dirname = ''; const process = { env: {} };`
9. Evaluate via `vm.runInContext(code, ctx, { timeout: 5000 })`.
10. Read `module.exports.X` for each expected name.

**Known fragility** — order matters. If you reorder steps 3 & 4, types leak and `SyntaxError`
surfaces at runtime. The audit caught this when `services-schema.ts` failed with
"Missing initializer in const declaration" because step 3 was collapsing `:` to `=`.

### 4.2 Why no `tsx` / `esbuild`?

- Build script must run in any Node environment (CI, dev, prod mirror).
- Adding a build-time dep just for parsing 4 TS files is overkill.
- Regex stripper covers ~100% of patterns present in `src/data/*.ts` files.
- If future TS files add exotic features (e.g. decorators), fall back to:
  `npx tsx scripts/build-entity-registry.mjs` (one-off, no install required).

## 5. Audit Metrics

### 5.1 Definitions

| Metric | Definition |
|---|---|
| `mentions_count` | Total occurrences of `entity.canonical_name` + `aliases` in any `.astro`/`.ts` file under `src/pages` or `src/components` (case-insensitive, word-boundary). |
| `link_count` | Number of `<a href="<entity.page_url>">` (with trailing slash optional). |
| `jsonld_refs` | Number of `"@id": "<absolute_url>"` or `"url": "<page_url>"` references in JSON-LD blocks. |
| `files_hit` | Count of distinct source files containing ≥1 mention/link/jsonld. |
| `coverage_score` | `min(100, mentions × 0.4 + links × 5 + jsonld × 3)` |

## 6. Key Findings → Action Items (Phase 2)

### F1. **Products & Capabilities are structurally invisible**
260 products + 458 processes = **718 entities** (83% of registry) have avg score 0-1.
The `/parts/[category]` and `/capabilities/[slug]` dynamic routes exist, but
no other page links to them — making them discoverable **only via sitemap**.

**Action:** Phase 2 will generate internal-link blocks:
- `/industries/X/` → "related parts" (top 8 by token overlap)
- `/materials/grade-X/` → "parts made from this grade" + "capabilities used"
- `/capabilities/X/` → "materials we apply this to" + "parts produced"
- `/parts/X/` → "industries served" + "standards met"

### F2. **Standards have zero internal presence**
18 standards (AMS 4911, AMS 4928, ASTM B265, etc.) are referenced in code but
not href-linked from any page. Schema.org `Product.conformsTo` exists in JSON-LD
but the audit didn't pick it up (regex too narrow).

**Action:** Audit script regex update + add standards sidebar in material pages
("We meet: AMS 4911, ASTM B348, ...")

### F3. **JSON-LD cross-references are not exploited**
0 entities found in JSON-LD `@id` graph. The `Organization.knowsAbout` array exists
but `Product.@id` / `Service.@id` cross-links are not generated per-entity.

**Action:** Phase 3 — entity-aware JSON-LD emitter (`scripts/build-entity-jsonld.mjs`)
that emits `@id` for every `/materials/`, `/parts/`, `/capabilities/` page and references
parent entities (`hasPart`, `material`, `usedIn`, `conformsTo`).

### F4. **Industry pages are the strongest cluster**
Industry avg score 59/100 — referenced everywhere. Use them as the
**hub pages** for the Phase 2 link mesh.

## 7. Closed-Loop Verification

The script pair forms a tight loop:

```
build-entity-registry.mjs → entity-registry.json (Single Source of Truth)
        ↓
audit-entity-coverage.mjs → coverage-report.{json,md}
        ↓
   (human or script decides: which orphans to link next)
        ↓
edit src/pages/.../*.astro  (add links)
        ↓
   re-run audit → score delta visible
        ↓
   iterate until avg score ≥ 60
```

**Re-run cadence:**
- After every content batch: `node scripts/audit-entity-coverage.mjs --top 20`
- Pre-deploy: full audit + commit coverage-report.md delta
- Quarterly: review `--missing` for entities that became orphans due to URL changes

## 9. Maintenance Notes

- **`data/entities/*.json` is build output.** Never hand-edit. Re-run `build-entity-registry.mjs`.
- **`coverage-report.md` is regenerable.** Commit only after intentional changes to `src/`.
- **Schema evolution:** if a new entity source appears (e.g. `content/products/`),
  add an extractor block to `build-entity-registry.mjs` after the existing 11.
- **Alias quality:** aliases drive audit accuracy. When a new entity lacks aliases,
  the audit silently misses it — always check `aliases.length ≥ 2` after build.
